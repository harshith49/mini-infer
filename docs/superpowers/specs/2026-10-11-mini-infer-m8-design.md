## Six-stage workload and execution

Extend `benchmarks/bench_stages.py` with an explicit `--suite all` mode producing `results/stages.csv`. Preserve its existing two-stage workload API and legacy default command/output for earlier tests and documented M2 commands. Reuse existing generation, static batching, scheduler, pool and quantization implementations. A small shared benchmark runner is appropriate where the stage and reference scripts need identical workload construction, completion metrics and CSV fields; avoid a general benchmark framework.

The default workload is eight seed-zero synthetic token-ID prompts with lengths `[16,64,32,128,16,64,32,128]`, output budgets `[4,32,8,64,4,32,8,64]`, maximum batch size two, one untimed warmup and three measured repetitions. CPU uses one PyTorch thread. Generation is greedy, has no EOS early stopping, and returns exactly 216 useful new tokens per repetition. Provide device, lengths, budgets, batch size, repetitions, threads, pool page size/count and output flags. Validate positive integers, matching nonempty lists, context limits including padded static cohorts, and individually feasible paged reservations before measurements. Synthetic tokens isolate inference and do not constitute a language-quality sample.

Run these stages in this order on the same prompt tensors and requested budgets:

1. `naive`: sequential independent requests, recomputing full prefixes.
2. `kv_cache`: sequential independent requests with contiguous KV caching.
3. `static_batching`: FIFO cached cohorts, each running to its largest budget; trim outputs to each requested budget and record excess computed tokens.
4. `continuous_batching`: the existing FIFO scheduler with contiguous request caches.
5. `paged_kv`: the same scheduler with a fixed shared page pool (default 32 pages of 16 tokens).
6. `int8`: the same paged scheduler after in-place weight-only conversion of the exclusively owned model. Record that this is the cumulative paged-plus-int8 stage.

Measure FP32 stages before conversion; do not keep an unused second model resident while measuring. Close scheduler/pool request state on success and failure. Completed outputs are retained only as needed for correctness checks and released between repetitions. Do not claim paged speed or capacity gains from these timing rows; the existing M5 allocation experiments provide separate evidence. Do not claim int8 token identity or faster execution.

Before publishing, all five FP32 stages must match independent cached generation exactly; existing public GPT-2/HF tests remain mandatory. Every measured repetition must have the expected output counts and deterministic tokens for its own stage. Int8 determinism is checked against its own warmup, and public-model quality must still satisfy the existing pinned Tiny Shakespeare perplexity gate (maximum 5% increase) with the existing scoring method. Quality evaluation is outside timing. Preserve the original M6 quality CSV rather than overwriting it; record the fresh quality result and source identity alongside M8 results.

## Metric definitions and output integrity

One successful invocation writes exactly one row per stage, in fixed order. Record device/hardware, Python/PyTorch versions, dtype, thread count, prompt lengths, budgets, seed, batch limit, cache backend, page configuration, warmups/repetitions, useful/excess token counts and workload description. Reject invalid configuration with an actionable CLI error; a failed stage or correctness check must not publish a partial six-stage result. Build rows first and replace the output only after the complete run succeeds.

Each repetition begins with common submission of all requests and ends after its last completion. Loading, tokenization, conversion, warmup, quality evaluation and post-run equality checks are excluded. Generation validation, allocations, cache copies, sampling and output materialization are included. For sequential requests, completion means return of that request; for static cohorts, return of its cohort; for scheduled requests, delivery of its completion event. Latency therefore includes waiting behind earlier requests. Synchronize CUDA at measurement boundaries and completion observations. Use useful tokens divided by median workload elapsed time for tokens/s; compute request completion p50/p95 over all measured repetitions using linear interpolation. Report seconds consistently and label these as whole-request latency, not per-token latency or TTFT.

`peak_memory_bytes` is the maximum PyTorch allocated-device peak across measured repetitions on CUDA, including the active model. CPU process peak remains blank with kind `unmeasured`; do not substitute RSS snapshots, analytical weights or KV reservation. Reset CUDA peak counters after loading/warmup and before each measured repetition. Report resident model tensor storage and stage-specific KV/pool/workspace byte scopes separately where measured or analytically defined, without presenting them as process peak. Explain retained CUDA allocator reservations are outside the allocated-tensor metric. CUDA values remain unmeasured in committed CPU results.
